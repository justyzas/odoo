## What this repo is

This is the Odoo ERP framework + apps monorepo, branch `19.0`. It contains:

- `odoo/` — the core framework: ORM, ORM registry, HTTP layer, module loader, CLI, low-level tooling. This is the kernel every addon depends on (via the implicit `base` module which lives at `odoo/addons/base/`).
- `addons/` — ~600 business/technical addon modules (sale, account, stock, mail, web, point_of_sale, hr, ...). Each is a self-contained Odoo module.

Odoo modules are pluggable: a module is a directory with a `__manifest__.py` declaring its `depends`, `data` (XML/CSV loaded on install), optional `demo` data, and `assets` bundles for the web client.

## Running the server

```
python odoo-bin [server options]
```

`odoo.conf` (gitignored) holds local DB connection settings and `addons_path = addons,odoo/addons`. It contains a real DB password locally — never print its contents or commit it.

Other odoo-bin subcommands: `shell` (interactive ORM shell against a DB), `db`, `module`, `i18n`, `scaffold` (generate a new module skeleton), `cloc`, `neutralize`, `populate`.

## Running Python tests

Odoo tests are `unittest`-based (see `odoo/tests/`), organized as test files inside each module's `tests/` directory, and executed through the server bootstrap rather than pytest directly.

```
python odoo-bin --test-enable --test-tags <spec> -d <database> --stop-after-init
```

- `--test-tags` filters by `[-][tag][/module][:class][.method]`, e.g.:
  - `/sale` — all tests in the `sale` module
  - `/sale:TestSaleOrder` — one test class
  - `/sale:TestSaleOrder.test_something` — one test method
  - `-at_install` / `post_install` — the two built-in phases (tests run `at_install` by default; use tags to opt into `post_install`)
- `--test-file=PATH` runs a single test file directly.
- Test-only "harness" modules live in `addons/test_*` (e.g. `test_orm`, `test_access_rights`, `test_lint`, `test_main_flows`) — these exist purely to exercise framework behavior and are not real business modules.

## Running JS/frontend tests

Frontend tests use **Hoot** (`addons/web/static/lib/hoot`), Odoo's in-house JS test framework — not Jest/Mocha. Test files live under each module's `static/tests/` directory (see `addons/web/static/tests/`). They run in-browser against a running Odoo server at `/web/tests`, filterable via `--test-tags` the same way as Python tests (e.g. `--test-tags /web.test_js[tag]`).

## Linting

Ruff is the linter/formatter for Python, config in `ruff.toml` (generated by runbot nightly checks — don't hand-edit lint rule selection without reason).

```
ruff check .
```

Notable local conventions from `ruff.toml`:
- isort section order: `future, standard-library, third-party, first-party (odoo), local-folder (odoo.addons)`.
- `E501` (line length) and several stylistic rules are intentionally disabled; `F401` unused-import is allowed in `__init__.py`.

## Architecture

### Module anatomy

Every addon follows the same shape:
- `__manifest__.py` — metadata, `depends`, `data`/`demo` XML/CSV load order, `assets` bundles.
- `models/` — ORM model definitions (`odoo.orm.models.Model`/`TransientModel`/`AbstractModel` subclasses).
- `views/` — XML view/action/menu definitions.
- `security/` — `ir.model.access.csv` (model-level CRUD access per group) and `ir_rules.xml` (record-level domains).
- `data/`, `demo/` — XML/CSV data records loaded at install/demo time.
- `wizard/` — transient models + views for multi-step user actions.
- `report/` — QWeb report templates.
- `static/src/` — web client (Owl components, JS, SCSS); `static/tests/` — Hoot tests.
- `tests/` — Python test cases, always guarded so they don't run outside the test runner.
- `i18n/` — translation `.po` files.

Module load order is resolved from the `depends` graph across all modules found on `addons_path` (`addons/`, `odoo/addons/`); XML/CSV in `data`/`demo` is loaded in the list order given in the manifest.

### ORM core (`odoo/orm/`)

- `models.py` / `model_classes.py` — base `Model` classes and the metaclass magic that merges a model's definition across every addon that extends it (`_inherit`).
- `fields.py` + `fields_*.py` — field type implementations (relational, numeric, temporal, textual, binary, selection, properties, reference).
- `registry.py` — the per-database `Registry`: the fully assembled set of models for a given DB, rebuilt on module install/upgrade.
- `environments.py` — `Environment`/`Cursor` context (the `self.env` you see everywhere: user, context, DB cursor).
- `domains.py` — the domain (search filter) DSL used throughout the ORM and `ir.rule`.

### Module system (`odoo/modules/`)

- `loading.py`, `module_graph.py` — dependency resolution and install/upgrade orchestration.
- `registry/` — registry bootstrapping, signaling across workers, caching.
- `db.py` — database creation/introspection.

### Security model

Two independent layers, both configured per-module under `security/`:
- `ir.model.access.csv` — coarse per-group, per-model read/write/create/unlink flags.
- `ir.rule` (`ir_rules.xml`) — record-level domain filters evaluated per group/user.
Never bypass these with `sudo()` without deliberately intending to escalate privilege for a specific, narrow reason.

### Web client

Built with **Owl** (Odoo's own reactive component framework, vendored under `addons/web/static/lib/owl`), not React/Vue. `addons/web/static/src/` is the core web client (`webclient/`, `views/`, `search/`, `core/`, `model/`). Other modules extend it by registering into shared registries and adding assets in their own manifest's `assets` key.

### Testing utilities

`odoo/tests/common.py` provides the base `TransactionCase`/`SavepointCase`-style test classes used throughout addons; tests are tagged (`@tagged`) with `standard`/`at_install`/`post_install` plus custom tags used for `--test-tags` filtering.
